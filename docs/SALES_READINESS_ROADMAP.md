# Kiwmee — แผนพัฒนาสู่การขายจริง (Sales Readiness Roadmap)

อัปเดต: 2 พ.ย. 2569 · อ้างอิง `CLAUDE.md`, `docs/HANDOFF.md`, `docs/LOYALTY_DESIGN.md`

## 1. สถานะปัจจุบัน (Production)

Kiwmee v2 ใช้งานได้จริงบน Railway (`kiwmee.up.railway.app`) สำหรับการจองคิวหลายร้าน, บิล, แบรนด์/สาขา และแอดมินร้าน

- การจองลูกค้า mobile-first พร้อม flow ตามร้าน, คิวว่าง, การยืนยัน/ยกเลิก/เลื่อนเองจากลิงก์ (#5, #11, #23)
- error หน้าจองเป็นภาษาไทย และชื่อลูกค้าเก็บตามที่พิมพ์ในแต่ละการจอง (#18)
- แอดมินร้าน: ภาพรวม, การจอง, บิล/รายรับ, ขั้นตอนจอง, บริการ/ราคา, ช่าง/สนาม, เวลาทำการ, ภาพร้าน/บริการ/ช่าง/สนาม (#10, #15, #25, #27, #28)
- ภาพจากเครื่องผ่าน Supabase Storage (`shop-media`) ด้วย JWT เจ้าของร้าน
- แบรนด์/สาขา, แพ็กเกจตาม plan (ตั้งด้วย SQL), บิล/คืนเงิน, ราคาตามเวลา (#15, #16)
- Super admin `/super`: ตั้งค่า LINE ของแพลตฟอร์ม (LIFF ID, Channel ID, token, secret) (#19) — **ยังไม่มีฟีเจอร์ที่ใช้ค่าเหล่านี้กับลูกค้า**
- unit tests 375, DB tests 87, build ผ่าน · CI (GitHub Actions) รันทั้งสามอย่างทุก PR
- เจ้าของร้านเชิญพนักงาน/เจ้าของร่วมได้เอง (#30)

## 2. หลักการก่อนขายจริง

1. ห้ามแตะ Supabase v1 (`rdbzdshvlfxenpsiyjzl`); ทุกอย่างอยู่ booking-v2
2. ทุก schema change ต้องเป็น migration ใหม่ และให้เจ้าของรัน SQL ก่อน merge
3. merge เข้า `main` = deploy อัตโนมัติ · CI ต้องเขียวก่อน merge
4. ทุกฟีเจอร์ต้องมี test และ verify บน production จริง
5. ฟีเจอร์ที่ยังไม่มี backend จริงต้องแสดงว่ายังไม่พร้อม ไม่ promise ล่วงหน้า

## 3. ช่องว่างสำคัญ (Sales Blockers)

### 3.1 ลูกค้ายังไม่ได้ยืนยันตัวตนด้วย LINE

- มีที่ตั้งค่า LINE แล้ว (`/super`) แต่ยังไม่มี LIFF login, การ์ดยืนยันนัด, การเตือนนัด
- ยังไม่มีหน้า "ของฉัน" ข้ามร้าน

### 3.2 ~~ร้านไม่รู้ตัวเมื่อมีการเปลี่ยนแปลง~~ (แก้แล้วในหน้าแอดมิน #32)

- ยังต้องเปิดหน้าแอดมินไว้ถึงจะเห็น · แจ้งผ่าน LINE ใน Phase 1 (ใช้ `booking_events` ชุดเดียวกัน)

### 3.3 ระบบสมาชิก/คะแนน/ระดับ/รางวัลยังไม่มี

- คะแนน, หมดอายุ, FIFO, คืนเงิน/คืนคะแนน
- ระดับสมาชิกจากยอดบิล, ตัวคูณ, บัตรตามระดับ
- รางวัลแบบคูปอง, จำกัดสิทธิ์, ช่วงแคมเปญ
- QR สมาชิก 60 วินาที

### 3.4 การชำระเงินและตรวจสลิปยังไม่เข้า v2 หน้าลูกค้า

- มี payment domain code แล้ว แต่หน้าลูกค้า/แอดมิน v2 ยังไม่ใช้ end-to-end
- ต้องย้าย payment/slip verification จาก v1 มา v2
- ต้องทดสอบ atomic confirmation, manual review, refund, timeout

### 3.5 ~~การเชิญพนักงานยังใช้ SQL มือ~~ (แก้แล้วใน #30)

- ยังไม่ส่งอีเมลเชิญเอง: เจ้าของร้านคัดลอกข้อความเชิญไปส่งทาง LINE/แชท (ส่งอีเมลอัตโนมัติภายหลัง)

### 3.6 ~~การจองที่ร้านบันทึกเองยังไม่มีลิงก์ลูกค้า~~ (แก้แล้วใน #35)

- ร้านส่งลิงก์ให้ลูกค้าได้ (คัดลอก / LINE / SMS) ทันทีหลังบันทึกการจอง หรือจากเมนู ⋯ ของการจอง · ลิงก์แสดงครั้งเดียว ส่งใหม่แล้วลิงก์เดิมใช้ไม่ได้

### 3.7 กฎหมายและการค้า

- **PDPA**: ระบบเก็บชื่อ เบอร์ และ LINE ID ของลูกค้าแทนร้าน → ต้องมีนโยบายความเป็นส่วนตัว, ข้อตกลงการใช้งาน (ร้าน ↔ Kiwmee),
  ข้อความแจ้งลูกค้าในหน้าจอง และวิธีลบ/ส่งออกข้อมูลลูกค้าเมื่อมีคำขอ
- **Kiwmee เก็บเงินร้านอย่างไร**: ช่วงแรกตั้งแพ็กเกจด้วย SQL + ออกใบแจ้งหนี้เอง · ระบบเก็บเงินอัตโนมัติภายหลัง
- **ค่าข้อความ LINE**: OA กลางของ Kiwmee จ่ายค่าข้อความ → ต้องจำกัดจำนวนการ์ดตามแพ็กเกจ (`docs/LOYALTY_DESIGN.md` §8)

### 3.8 คุณภาพและปฏิบัติการ

- v1 code ยังอยู่ใน repo
- ไม่มี monitoring/alerting สำหรับ production
- **ยังไม่ได้ตรวจว่า booking-v2 มี backup รายวัน** (แพ็กเกจ Supabase ต่างกัน) และยังไม่เคยลองกู้คืน
- ไม่มี SLA/support process

## 4. Roadmap ตามลำดับ

### Phase 0 — Stabilize current product (1–2 สัปดาห์)

เป้าหมาย: ทำให้ v2 ปัจจุบันพร้อมขาย "ระบบจอง + บิล" โดยไม่พึ่ง LINE

- ✅ error ภาษาไทยในหน้าจอง · ✅ ชื่อลูกค้าเมื่อเบอร์ซ้ำ (#18)
- ✅ CI: `npm test`, `npm run test:db`, `next build` ทุก PR
- ✅ หน้าเชิญพนักงาน: owner ชวน staff/เจ้าของร่วมด้วยอีเมล, เปลี่ยนสิทธิ์, เอาออก (#30)
- ✅ แจ้งร้าน**ในหน้าแอดมิน**เมื่อมีการจองใหม่/ยกเลิก/เลื่อน (ตัวเลขที่ยังไม่อ่าน + เช็กทุก 30 วินาที) — ผ่าน LINE ใน Phase 1 (#32)
- ✅ บันทึกประวัติการเลื่อนโดยลูกค้า (`booking_events`, #32)
- ✅ ลิงก์จัดการการจองสำหรับการจองที่ร้านบันทึกเอง (#35)
- ตรวจ backup ของ booking-v2 และลองกู้คืน 1 ครั้ง (ไปที่โปรเจกต์ทดสอบ) — เครื่องมือพร้อมแล้ว: `docs/BACKUP_RESTORE.md` + `scripts/backup-drill.sh` (CI รันทุก PR, #70) · เหลือเจ้าของตรวจว่า Supabase แผนปัจจุบันมี backup อัตโนมัติหรือไม่
- อัปเดต `docs/HANDOFF.md` ทุก PR

Exit criteria:
- ร้านจริง 1–3 ร้านใช้งานได้โดยไม่ต้องใช้ SQL มือ (ยกเว้นตั้งแพ็กเกจ)
- ไม่มี P0 bug ที่ทำให้จอง/บิลเสีย · CI เขียว
- รู้ว่า backup มีจริงและกู้ได้

**→ เริ่มทดลองกับร้านจริง (pilot) ได้หลังจบ Phase 0** — ระบบจอง + บิล ใช้ได้โดยไม่ต้องมี LINE

### Phase 1 — LINE identity and notifications (2–3 สัปดาห์)

เป้าหมาย: ลูกค้าล็อกอินด้วย LINE และร้านได้แจ้งเตือน

- LINE Login channel + LIFF app + Messaging API channel (provider เดียวกัน) — ตั้งค่าใน `/super` แล้ว
- LIFF login ในหน้าจอง
- การ์ดยืนยันการจอง + ลิงก์จัดการการจอง
- เตือนนัด
- หน้า "ของฉัน" ใน LIFF: นัดที่จะถึง + ประวัติข้ามร้าน
- แจ้งร้านผ่าน LINE เมื่อมีการจอง/ยกเลิก/เลื่อน
- จำกัดจำนวนการ์ดตามแพ็กเกจ (คุมค่าข้อความ)
- PDPA ขั้นต่ำ: นโยบายความเป็นส่วนตัว + ข้อความยินยอมในหน้าจอง/LIFF

Exit criteria:
- ลูกค้าเดียวกันข้ามร้านใช้ `line_user_id` เดียวกัน
- การแจ้งเตือนไปถึงลูกค้าและร้านจริง
- ไม่มี userId ไม่ตรงกันข้าม provider

**→ เปิดขายแพ็กเกจแรก (จอง + บิล + LINE) ได้หลังจบ Phase 1** — ตั้งแพ็กเกจด้วย SQL + ออกใบแจ้งหนี้เอง

### Phase 2 — Loyalty core (3–4 สัปดาห์)

เป้าหมาย: เปิดระบบสมาชิก/คะแนน/ระดับ/รางวัลตาม `docs/LOYALTY_DESIGN.md`

- กติกาคะแนนต่อแบรนด์
- ได้คะแนนตอนปิดบิลจากยอดที่จ่ายจริง · ปัดเศษทิ้ง
- คืนเงินดึงคะแนนคืนตามสัดส่วน
- หมดอายุ + เตือน 14 วัน · FIFO ใช้ล็อตที่หมดอายุก่อน
- ระดับสมาชิกจากยอดบิลย้อนหลัง (ไม่เกิน 5 ระดับ) · ตัวคูณคะแนนและรางวัลเฉพาะระดับ · บัตรตามระดับ
- รางวัลแบบคูปอง: รูป, จำนวนสิทธิ์, จำกัดต่อคน, ช่วงแคมเปญ
- QR สมาชิก 60 วินาที

Exit criteria:
- ปิดบิลแล้วได้คะแนนจริง · คืนเงินแล้วคะแนนถูกดึงคืน
- คะแนนหมดอายุและเตือนทำงาน
- ระดับ/รางวัลทำงานตามกติกา

### Phase 3 — Payment and slip verification (2–3 สัปดาห์)

เป้าหมาย: ลูกค้าชำระเงิน/แนบสลิป และร้านตรวจสอบได้ (รวมการย้ายระบบชำระเงินของ v1 ทั้งหมด)

- ย้าย payment/slip verification จาก v1 มา v2
- ลูกค้าแนบสลิปในหน้าจอง · ตรวจยอด/ผู้รับ/เวลา
- manual review · timeout handling · refund flow · audit trail
- มัดจำ (`bill_payments.kind = deposit` มีในตารางแล้ว)

Exit criteria:
- payment ที่ถูกต้องยืนยันได้
- ยอดไม่ตรง/ผู้รับไม่ตรง ไม่ auto-confirm
- timeout ไม่ทำให้ข้อมูลเสีย
- refund ทำงานครบ

> ลำดับ Phase 2 ↔ 3: ร้านเสริมสวย/ตัดผมส่วนใหญ่จ่ายหน้าร้าน → สมาชิกก่อน · ถ้าลูกค้ากลุ่มแรกเป็นสนามกีฬาที่ต้องเก็บมัดจำ → สลับเอา Phase 3 ก่อน

### Phase 4 — Booking rewards (1–2 สัปดาห์)

เป้าหมาย: ลูกค้าเลือกรางวัลตอนจอง

- hold/redeem/release reward
- ใช้ได้ทีละ 1 รางวัลต่อบิล · คะแนนที่เหลือเก็บต่อ

Exit criteria:
- ลูกค้าใช้รางวัลได้โดยไม่ทำให้ booking ผิดพลาด
- ถ้า reward หมด/ไม่พร้อม ระบบ fail อย่างปลอดภัย

### Phase 5 — Commercial packaging and onboarding (1–2 สัปดาห์)

เป้าหมาย: ทำให้ขายได้เองโดยไม่ต้องมีคนช่วยตั้งค่า

- หน้าราคา/แพ็กเกจ (ฟรี, เริ่มต้น, โปร, สมาชิก) · ระบบเก็บเงินค่าแพ็กเกจ
- self-service onboarding ร้านใหม่
- import/export ข้อมูลพื้นฐาน · ลบ/ส่งออกข้อมูลลูกค้าตามคำขอ (PDPA)
- documentation สำหรับร้าน · support process
- monitoring/alerting · ลบโค้ด v1

Exit criteria:
- ร้านใหม่เปิดใช้งานและจ่ายเงินได้เองโดยไม่ต้อง SQL
- owner ตั้งค่า บริการ, ราคา, เวลาทำการ, ภาพ, พนักงานได้เอง
- มี rollback, backup และ monitoring

## 5. ลำดับความสำคัญสำหรับการขายแรก

1. ระบบจอง + บิล + แบรนด์/สาขา (Phase 0) → **pilot**
2. LINE identity + แจ้งเตือน (Phase 1) → **เปิดขายแพ็กเกจแรก**
3. ระบบสมาชิก/คะแนน/ระดับ/รางวัล (Phase 2) → แพ็กเกจโปร/สมาชิก
4. Payment/slip verification (Phase 3)
5. Booking rewards (Phase 4)
6. Commercial packaging/onboarding (Phase 5)

## 6. สิ่งที่ไม่ควรทำก่อนขายจริง

- อย่า promise ฟีเจอร์ที่ backend ยังไม่มี
- อย่าใช้ stock image แทนรูปร้านจริง
- อย่าให้ staff เห็น cross-tenant data
- อย่า merge migration ก่อนให้เจ้าของรัน SQL · อย่า merge ตอน CI แดง
- อย่า deploy โดยไม่ verify production
- อย่าเก็บข้อมูลลูกค้าจริงโดยไม่มีนโยบายความเป็นส่วนตัว

## 7. Definition of Done สำหรับ "ขายได้จริง"

- ร้านใหม่เปิดใช้งานได้เอง
- ลูกค้าจอง/ยกเลิก/เลื่อนได้ด้วย LINE
- ร้านได้แจ้งเตือนและจัดการการจองได้
- บิล/รายรับ/คืนเงินทำงานครบ
- คะแนน/ระดับ/รางวัลทำงานตามกติกา
- ชำระเงิน/ตรวจสลิป/refund ทำงาน
- ไม่มี P0/P1 bug ที่กระทบการจองหรือการเงิน
- มี backup, monitoring, support process
- มีนโยบายความเป็นส่วนตัว ข้อตกลงการใช้งาน และเอกสารสำหรับร้านและผู้ดูแล
