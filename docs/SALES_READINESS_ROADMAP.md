# Kiwmee — แผนพัฒนาสู่การขายจริง (Sales Readiness Roadmap)

อัปเดต: 2 พ.ย. 2569 · อ้างอิง `CLAUDE.md`, `docs/HANDOFF.md`, `docs/LOYALTY_DESIGN.md`

## 1. สถานะปัจจุบัน (Production)

Kiwmee v2 ใช้งานได้จริงบน Railway (`kiwmee.up.railway.app`) สำหรับการจองคิวหลายร้าน, บิล, แบรนด์/สาขา และแอดมินร้าน

- การจองลูกค้า mobile-first พร้อม flow ตามร้าน, คิวว่าง, การยืนยัน/ยกเลิก/เลื่อน
- แอดมินร้าน: ภาพรวม, การจอง, บิล/รายรับ, ขั้นตอนจอง, บริการ/ราคา, ช่าง/สนาม, เวลาทำการ, ภาพร้าน/บริการ/ช่าง/สนาม
- ภาพจากเครื่องได้แล้ว ผ่าน Supabase Storage (`shop-media`) ด้วย JWT เจ้าของร้าน
- แบรนด์/สาขา, แพ็กเกจตาม plan, บิล/คืนเงิน, คิวว่าง, ราคาตามเวลา
- Super admin: ตั้งค่า LINE platform settings
- ทดสอบ unit ผ่าน 378+ รายการ, DB tests ผ่าน 79+ รายการ, build ผ่าน

## 2. หลักการก่อนขายจริง

1. ห้ามแตะ Supabase v1 (`rdbzdshvlfxenpsiyjzl`); ทุกอย่างอยู่ booking-v2
2. ทุก schema change ต้องเป็น migration ใหม่ และให้เจ้าของรัน SQL ก่อน merge
3. merge เข้า `main` = deploy อัตโนมัติ
4. ทุกฟีเจอร์ต้องมี test และ verify บน production จริง
5. ฟีเจอร์ที่ยังไม่มี backend จริงต้องแสดงว่ายังไม่พร้อม ไม่ promise ล่วงหน้า

## 3. ช่องว่างสำคัญ (Sales Blockers)

### 3.1 ลูกค้าต้องยืนยันตัวตนด้วย LINE

- ยังไม่มี LIFF login, การ์ดยืนยันนัด, การแจ้งเตือน
- ลูกค้าที่ใช้เบอร์เดียวกันยังอาจได้ชื่อคนแรก
- ยังไม่มีหน้า “ของฉัน” ข้ามร้าน
- ยังไม่มีการแจ้งร้านเมื่อมีการจองใหม่/ยกเลิก/เลื่อน

### 3.2 ระบบสมาชิก/คะแนน/ระดับ/รางวัลยังไม่มี

- คะแนน, หมดอายุ, FIFO, คืนเงิน/คืนคะแนน
- ระดับสมาชิกจากยอดบิล, ตัวคูณ, บัตรตามระดับ
- รางวัลแบบคูปอง, จำกัดสิทธิ์, ช่วงแคมเปญ
- QR สมาชิก 60 วินาที

### 3.3 การชำระเงินและตรวจสลิปยังไม่เข้า v2 หน้าลูกค้า

- มี payment domain code แล้ว แต่หน้าลูกค้า/แอดมิน v2 ยังไม่ใช้ end-to-end
- ต้องย้าย payment/slip verification จาก v1 มา v2
- ต้องทดสอบ atomic confirmation, manual review, refund, timeout

### 3.4 การเชิญพนักงานยังใช้ SQL มือ

- ยังไม่มีหน้าเชิญ/จัดการสมาชิกร้าน
- ต้องสร้าง flow สำหรับ owner ชวน staff และกำหนดสิทธิ์

### 3.5 การจองที่ร้านบันทึกเองยังไม่มีลิงก์ลูกค้า

- ต้องสร้าง manage token และส่งให้ลูกค้า
- ต้องรองรับเลื่อน/ยกเลิกตามนโยบายร้าน

### 3.6 คุณภาพและปฏิบัติการ

- ไม่มี CI
- v1 code ยังอยู่ใน repo
- ไม่มี monitoring/alerting สำหรับ production
- ไม่มี backup/restore drill
- ไม่มี SLA/support process

## 4. Roadmap ตามลำดับ

### Phase 0 — Stabilize current product (1–2 สัปดาห์)

เป้าหมาย: ทำให้ v2 ปัจจุบันพร้อมขาย “ระบบจอง + บิล” โดยไม่พึ่ง LINE

- แก้ error ภาษาไทยในหน้าจอง
- แก้ชื่อลูกค้าเมื่อเบอร์ซ้ำ
- แจ้งร้านเมื่อมีการจองใหม่/ยกเลิก/เลื่อน
- บันทึกประวัติการเลื่อนโดยลูกค้า
- เพิ่มหน้าเชิญพนักงาน
- เพิ่มลิงก์จัดการการจองให้การจองที่ร้านบันทึกเอง
- เพิ่ม CI อย่างน้อย `npm test` และ `next build`
- อัปเดต `docs/HANDOFF.md` ทุก PR

Exit criteria:
- ร้านจริง 1–3 ร้านใช้งานได้โดยไม่ต้องใช้ SQL มือ
- ไม่มี P0 bug ที่ทำให้จอง/บิลเสีย

### Phase 1 — LINE identity and notifications (2–3 สัปดาห์)

เป้าหมาย: ลูกค้าล็อกอินด้วย LINE และร้านได้แจ้งเตือน

- LINE Login channel + LIFF app + Messaging API channel (provider เดียวกัน)
- LIFF login ในหน้าจอง
- การ์ดยืนยันการจอง + ลิงก์จัดการการจอง
- เตือนนัด
- หน้า “ของฉัน” ใน LIFF: นัดที่จะถึง + ประวัติข้ามร้าน
- แจ้งร้านเมื่อมีการจอง/ยกเลิก/เลื่อน

Exit criteria:
- ลูกค้าเดียวกันข้ามร้านใช้ `line_user_id` เดียวกัน
- การแจ้งเตือนไปถึงลูกค้าและร้านจริง
- ไม่มี userId ไม่ตรงกันข้าม provider

### Phase 2 — Loyalty core (3–4 สัปดาห์)

เป้าหมาย: เปิดระบบสมาชิก/คะแนน/ระดับ/รางวัลตาม `docs/LOYALTY_DESIGN.md`

- กติกาคะแนนต่อร้าน
- ได้คะแนนตอนปิดบิลจากยอดที่จ่ายจริง
- ปัดเศษทิ้ง
- คืนเงินดึงคะแนนคืนตามสัดส่วน
- หมดอายุ + เตือน 14 วัน
- FIFO ใช้ล็อตที่หมดอายุก่อน
- ระดับสมาชิกจากยอดบิลย้อนหลัง (ไม่เกิน 5 ระดับ)
- ตัวคูณคะแนนและรางวัลเฉพาะระดับ
- บัตรตามระดับ
- รางวัลแบบคูปอง: รูป, จำนวนสิทธิ์, จำกัดต่อคน, ช่วงแคมเปญ
- QR สมาชิก 60 วินาที

Exit criteria:
- ปิดบิลแล้วได้คะแนนจริง
- คืนเงินแล้วคะแนนถูกดึงคืน
- คะแนนหมดอายุและเตือนทำงาน
- ระดับ/รางวัลทำงานตามกติกา

### Phase 3 — Payment and slip verification (2–3 สัปดาห์)

เป้าหมาย: ลูกค้าชำระเงิน/แนบสลิป และร้านตรวจสอบได้

- ย้าย payment/slip verification จาก v1 มา v2
- ลูกค้าแนบสลิปในหน้าจอง
- ตรวจยอด/ผู้รับ/เวลา
- manual review
- timeout handling
- refund flow
- audit trail

Exit criteria:
- payment ที่ถูกต้องยืนยันได้
- ยอดไม่ตรง/ผู้รับไม่ตรง ไม่ auto-confirm
- timeout ไม่ทำให้ข้อมูลเสีย
- refund ทำงานครบ

### Phase 4 — Booking rewards (1–2 สัปดาห์)

เป้าหมาย: ลูกค้าเลือกรางวัลตอนจอง

- hold/redeem/release reward
- ใช้ได้ทีละ 1 รางวัลต่อบิล
- คะแนนที่เหลือเก็บต่อ
- ย้ายระบบชำระเงิน/ตรวจสลิปของ v1 ให้สมบูรณ์

Exit criteria:
- ลูกค้าใช้รางวัลได้โดยไม่ทำให้ booking ผิดพลาด
- ถ้า reward หมด/ไม่พร้อม ระบบ fail อย่างปลอดภัย

### Phase 5 — Commercial packaging and onboarding (1–2 สัปดาห์)

เป้าหมาย: ทำให้ขายได้จริงและ onboarding ร้านใหม่ได้เอง

- หน้าราคา/แพ็กเกจ (ฟรี, เริ่มต้น, โปร, สมาชิก)
- self-service onboarding ร้านใหม่
- เชิญพนักงานผ่าน UI
- import/export ข้อมูลพื้นฐาน
- documentation สำหรับร้าน
- support process
- CI/CD และ monitoring

Exit criteria:
- ร้านใหม่เปิดใช้งานได้เองโดยไม่ต้อง SQL
- owner ตั้งค่า LINE, บริการ, ราคา, เวลาทำการ, ภาพได้เอง
- มี rollback และ backup plan

## 5. ลำดับความสำคัญสำหรับการขายแรก

1. ระบบจอง + บิล + แบรนด์/สาขา
2. LINE identity + แจ้งเตือน
3. ระบบสมาชิก/คะแนน/ระดับ/รางวัล
4. Payment/slip verification
5. Booking rewards
6. Commercial packaging/onboarding

## 6. สิ่งที่ไม่ควรทำก่อนขายจริง

- อย่า promise ฟีเจอร์ที่ backend ยังไม่มี
- อย่าใช้ stock image แทนรูปร้านจริง
- อย่าให้ staff เห็น cross-tenant data
- อย่า merge migration ก่อนให้เจ้าของรัน SQL
- อย่า deploy โดยไม่ verify production

## 7. Definition of Done สำหรับ “ขายได้จริง”

- ร้านใหม่เปิดใช้งานได้เอง
- ลูกค้าจอง/ยกเลิก/เลื่อนได้ด้วย LINE
- ร้านได้แจ้งเตือนและจัดการการจองได้
- บิล/รายรับ/คืนเงินทำงานครบ
- คะแนน/ระดับ/รางวัลทำงานตามกติกา
- ชำระเงิน/ตรวจสลิป/refund ทำงาน
- ไม่มี P0/P1 bug ที่กระทบการจองหรือการเงิน
- มี backup, monitoring, support process
- มีเอกสารสำหรับร้านและผู้ดูแล

## 8. งานถัดไปที่แนะนำ

เริ่มจาก Phase 0 ก่อน เพื่อให้ระบบจอง/บิลเสถียร จากนั้นทำ Phase 1 (LINE) เพราะเป็นฐานของระบบสมาชิกและแจ้งเตือน
